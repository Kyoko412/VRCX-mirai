# 有共同好友的同房相遇次数：设计草案

状态：已按本草案实现。目标是在 VRCX 的「房内玩家」页面中，只为**与你有共同好友**的其他玩家累计「已确认同房次数」。这里的「同房」表示你们同时出现在同一个 VRChat 实例，不表示实际交谈或靠近。

## 用户能看到什么

- 当前房间玩家仍按现有方式展示；新功能不隐藏没有共同好友的玩家。
- 对每个能识别身份的其他玩家，显示「共同好友 N 位」或「共同好友状态无法确认」，并显示「已确认同房 N 次」。没有共同好友的人本次不增加次数。
- 点击玩家可查看已计入的相遇明细：日期、地图、实例、当次查到的共同好友数量。旧的资料页「见面的次数」保留原意，避免把两种算法混为一谈。
- 例子：你在周一和玩家 A 同房，查到 2 位共同好友，计 1 次；周三再次同房且仍查到至少 1 位，计第 2 次。仅刷新玩家列表不会增加次数。

## 本草案采用的计数规则

1. 排除当前账号自己。已是好友和非好友的玩家都纳入候选；判断条件仅是「与你至少有 1 位共同好友」，不把共同群组算作共同好友。
2. **一次你自己的房间访问 + 同一位玩家，最多计 1 次。** 对方在这次访问中离开后又回来，不重复计数；你离开并重新进入，即使是同一个实例，也视为新的一次访问。
3. 资格以**这次同房期间成功查询到的共同好友状态**为准，并保存当次结果。之后好友关系变化，不追改已确认的历史次数。
4. 只有成功查到共同好友数量大于 0 才计入。明确查到 0 位则不计入。查询失败、权限限制或缺少稳定玩家 ID 时标记「无法确认」，不能当成 0 位，也不能加次数。
5. 「已确认同房次数」只统计 VRCX 观察并成功确认的记录，不宣称是 VRChat 全部历史。

本版采用「已是好友的玩家也算」和「对方在同一次你的房间访问中离开又回来仍只算一次」。

## 现有代码能复用什么

| 数据或界面                                                      | 目前情况                                 | 在新功能中的用途                     |
| --------------------------------------------------------------- | ---------------------------------------- | ------------------------------------ |
| `src/views/PlayerList/PlayerList.vue`、`src/stores/instance.js` | 已展示当前实例玩家                       | 增加共同好友状态及相遇次数的展示位置 |
| `src/coordinators/gameLogCoordinator.js`                        | 处理地图切换、玩家加入和离开事件         | 识别同房候选及访问边界               |
| `gamelog_location`、`gamelog_join_leave`                        | 已保存位置、玩家 ID、时间和加入/离开事件 | 作为本机观察记录；缺失日志不能补造   |
| `src/api/user.js` 的 `getMutualCounts`                          | 可按玩家 ID 查询共同好友数量             | 判断当次是否满足 `friends > 0`       |
| 资料页旧「见面的次数」                                          | `getUserStats` 按不同 `location` 计数    | 保留为旧统计，不直接用于新次数       |

`src/services/database/mutualGraph.js` 缓存的是已抓取好友的关系图，不能假定它覆盖房间内的所有非好友。因此不能仅凭该图判断某个陌生人「没有共同好友」。

## 推荐的数据流

1. VRCX 从游戏日志读到你进入一个实例，建立一条「我的本次房间访问」标识。标识由账号、进入时间和实例位置组成，不仅使用实例 ID，因为同一个实例可能多次进入。
2. 读到房内其他玩家的加入事件，或恢复运行中的玩家列表时，在能够找到对应「我的房间访问」记录的前提下，用稳定的 `user_id` 建立候选。同一访问中的重复加入事件归并到同一候选；找不到访问边界时仅显示当前玩家，不增加次数。
3. 候选进入限速查询队列，通过现有共同好友接口查询 `friends` 数量。一次房间访问中同一玩家只发起一次有效查询；429 等暂时失败可退避重试，但不反复在每次界面刷新时请求。
4. 在双方仍被观察为同房期间得到成功结果后，把 `> 0`、`= 0` 或「无法确认」连同查询时间保存。若离开前仍未取得结果，保持「无法确认」，不在日后用新的好友关系补判这次历史。
5. 页面从本地记录统计 `status = qualified` 的行数，并展示当次状态。无需把一个可变的总次数作为唯一真相单独累加；这样日志重放或应用重启也不会重复加数。

建议新增一个按当前账号隔离的本地表，例如 `${userPrefix}_mutual_encounters_v1`：

| 字段                                | 含义                                       |
| ----------------------------------- | ------------------------------------------ |
| `visit_key`                         | 我本次进入房间的稳定标识                   |
| `other_user_id`                     | 对方 VRChat 用户 ID                        |
| `location`、`observed_at`           | 实例与首次观察到同房的时间                 |
| `display_name_snapshot`             | 当时昵称，仅用于展示；身份仍以用户 ID 为准 |
| `status`                            | `qualified`、`not_qualified` 或 `unknown`  |
| `mutual_friend_count`、`checked_at` | 当次成功查询的数量和时间；未成功时为空     |

对 `(visit_key, other_user_id)` 建唯一约束；按 `other_user_id, status` 建查询索引。只在 `qualified` 时给可见计数增加 1。保存 `not_qualified` 和 `unknown` 是为了在日志重放时保持当时的判定，避免后来好友关系改变造成误计。

## 可行性边界与显示规则

- VRChat 用户可以关闭「Show Mutual Connections」。这类限制，以及当前账号关闭共同关系、接口报错或被限流，都应显示「无法确认」，而非「没有共同好友」。[VRChat 官方说明](https://wiki.vrchat.com/wiki/Social#Mutuals)。
- 游戏日志被禁用、VRCX 没有观察到某段时间、加入事件没有可靠用户 ID、用户被屏蔽或日志格式改变，都可能让同房记录不完整。只使用显示名合并身份会误认改名或同名玩家，因此缺少 ID 的记录不自动计数。
- 已有旧日志能证明部分历史同房，却不能证明当时是否有共同好友。首版从功能启用后开始「已确认次数」；如以后提供历史回算，必须另标「按当前关系估算」，不得混入已确认次数。
- 同一房间可能有很多玩家。共同好友请求应排队、缓存单次访问内结果，并尊重接口错误和退避，不在列表每次刷新时查询所有人。

## 其他方案与取舍

| 方案                                       | 优点                         | 问题                                                             |
| ------------------------------------------ | ---------------------------- | ---------------------------------------------------------------- |
| **推荐：相遇时确认并保存快照**             | 次数稳定；能说明每次为何计入 | 当次接口不可用时只能标记无法确认；需要小型新表和请求队列         |
| 查询时按当前共同好友关系筛选全部旧同房记录 | 可利用旧日志，初版工作较少   | 加好友或删好友会让过去的次数突然变化，无法表示相遇当时的状态     |
| 仅改旧「见面的次数」的 SQL                 | 表面改动最少                 | 旧计数是不同实例数，无法准确表示重复相遇，也无法保存共同好友判定 |

## 验收用例

1. 玩家 A 与你有共同好友：第一次同房显示 1 次；离开该实例后再次进入并同房显示 2 次。
2. 同一次你的房间访问里，A 离开又回来、应用重启后重新读取日志，次数仍只增加 1。
3. 玩家 B 确认没有共同好友：不增加；玩家 C 查询受限：显示无法确认，不增加，也不把 C 标成「0 位」。
4. 自己、缺少玩家 ID 的记录均不增加；改名不把同一 ID 分成两个人。
5. 已确认历史在共同好友关系变化后保持不变；切换 VRCX 账号不会混用计数。
6. 进入多人房间、遇到接口 429、游戏日志关闭或缺失时，页面仍可用且不会重复请求或虚构次数。

## 实施范围

已增加同房会话判定逻辑、共同好友查询队列及状态、本地记录表、房内玩家列与玩家明细、对应测试。历史游戏日志不会触发共同好友回算；只恢复当前房间仍在场的玩家。

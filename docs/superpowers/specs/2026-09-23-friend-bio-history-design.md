# 好友简介历史：讨论草案

状态：**已实现**。参考截图用于说明期望的交互，不照搬其代码或假定它的数据来源。目标是在 VRCX 的好友详情中，查看本机曾观察到的简介版本、变化时间和新旧文本差异。

## 用户看到的内容

- 在好友详情「信息」页的当前简介标题旁放「简介历史」入口。点击后打开可滚动的弹窗，顶部显示当前资料页返回的简介；下方按时间倒序列出本地记录。
- 每条记录显示观察时间、修改前后文本，以及红色删除、绿色新增的差异。长简介先折叠，可点「显示完整文本」展开，保留原始换行。
- 标题写「本机记录到 N 次简介变化」。没有记录时显示「暂无本机记录」；不把它解释为好友从未修改过简介。
- 当前简介与最近一条记录的新文本不一致时，仍显示当前简介，但标明「当前版本的变化时间未记录」。只有两者一致时，才可显示「最近记录于……」。

截图中的「更新于 7 天、11 小时」不能直接当作 VRChat 的真实编辑时间。项目目前保存的是 VRCX **观察到变化的时间**；好友可能在离线期间多次修改，VRCX 只能记录后来看到的结果。

目前的写入流程只处理**已在好友列表中的人**，而且首次加载某人的资料只是建立缓存，不生成一条「历史修改」。现有旧记录可展示，但不能补出应用未观察到的版本。换 VRCX 账号或设备时，本地历史也不自动合并。

## 方案比较

1. **推荐：复用本地简介事件表。** 加按 `user_id, created_at DESC, id DESC` 的索引和按用户分页读取方法；沿用既有好友变化检测，补齐空字符串转换。优点是可以立即利用已有记录，改动小，时间与来源明确。
2. 打开资料页时把当前简介也当成一个新版本保存。容易出现重复记录，把「第一次看到」误报为「修改」；若以后需要基线，应单独标成「首次观察」，不计入修改次数。
3. 另建完整快照表并定时抓取所有好友。可以增加观察频率，但请求和存储成本高，依然无法还原未观察期间的每次修改；首版不采用。

## 推荐的数据与界面流程

1. 用户打开好友详情的「简介历史」时，以稳定的 `user_id` 查询**当前登录账号**的本地 `feed_bio`，按 `created_at DESC, id DESC` 分页，先取 30～50 条；总数单独查询。昵称只用于展示，不作为身份键。关闭弹窗后不持续查询。
2. 列表只计入新旧内容确实不同的观察事件。`A → B → A` 是两次真实观察到的变化，不能仅按文本去重；同一次事件重复写入则应在写入路径去重。`id` 用于同一时间戳下的稳定排序和翻页。
3. 简介变成空白或从空白变为文字时也保存事件；空白在界面显示为「空简介」，不当作数据缺失。首次取得好友简介可以展示为当前值，但不伪造一条过去的修改。
4. 差异展示复用现有 Feed 算法的语义，抽到独立工具并测试；不得把未经转义的好友简介直接插入 HTML。短预览、完整文本及差异视图均保留换行。
5. 时间显示为用户本地时区的「VRCX 观察时间」。资料页当前值来自现有用户资料查询，本地历史查询不额外向 VRChat 请求历史。数据库读取失败时显示错误和重试入口。

## 验收例子

- 已存 `A → B`、`B → C` 两条：显示本机记录 2 次，最新记录在前；展开后能看旧、新原文及红绿差异。
- 从空白变成 `Hello`、再清空：两次都可记录，空白不显示成「未知」。
- 好友改名：仍通过用户 ID 找到原有简介历史。
- VRCX 没运行时好友改了几次：只展示后来观察到的状态变化，不虚构中间版本或实际修改时间。
- 100 条以上历史：分页追加，不一次性渲染全部；重复时间戳不漏页、不重页。
- 当前简介与最新本地记录不同：当前简介仍可读，但不显示未经证实的「更新于」时间。

## 已采用的界面选择

- 对当前好友和已解除好友显示入口，只要仍能打开其用户详情；历史按 ID 保留。
- 首版只在本机查看，不增加导出。
